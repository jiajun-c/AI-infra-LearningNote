# 函数调用

## 1. 开销分解

`result = foo(a, b, c)` 整个调用流程如下所示：

```cpp
┌──────────────────────────────────────┐
│ 1. 参数准备：放入寄存器 / 压栈          │
│ 2. CALL 指令：PC 跳转                 │
│ 3. 函数序言：                         │
│      - 栈帧分配（push rbp / sub rsp）  │
│      - 保存 callee-saved 寄存器       │
│ 4. 函数体执行                         │
│ 5. 函数尾声：                         │
│      - 恢复 callee-saved 寄存器       │
│      - 栈帧释放（leave / add rsp）    │
│ 6. RET 指令：PC 返回                  │
└──────────────────────────────────────┘
```

## 2. C/C++ 调用约定的具体成本

以 System V AMD64（Linux x86_64）为例，单次普通函数调用各步骤的典型开销：

|步骤|典型 cycle|备注|
|---|---|---|
|参数入寄存器|0|ABI 友好时已经就在寄存器里|
|参数压栈|1~2 / 参数|参数超过 6 个时累加|
|CALL 指令|~1|同时压入返回地址|
|函数序言|3~5|保存寄存器、`sub rsp`|
|返回值准备|0~1|写 `rax`|
|函数尾声|3~5|恢复寄存器、`add rsp`|
|RET|~1|—|
|**合计**|**~10~20**|**@3GHz 约 3~7 ns**|

## 3. 各类函数的开销

### 3.1 普通函数

```cpp
int add(int a, int b) { return a + b; }
```

编译器**通常会自动内联**，开销 ≈ 0。如果不内联，开销 ≈ 10~20 cycle，但函数体本身只有 1 cycle —— **20 倍放大**。

### 3.2 大函数

```cpp
void big_func() {
    char buf[4096];      // 4KB 栈帧
    int arr[1000];       // 4KB 栈帧
    // ...
}
```

开销显著增加：

- 栈帧分配要 `sub rsp, 8192` —— 单条指令但扰动栈顶 cache
- 函数体一上来就要 `sub rsp` 一下
- 栈空间占用大，破坏 cache 局部性
- 返回时要恢复栈帧

### 3.3 虚函数

```cpp
class Base {
public:
    virtual void foo() = 0;
};

class Derived : public Base {
    void foo() override { /* ... */ }
};

Base* p = new Derived();
p->foo();   // ← 这次调用要走 vtable
```

开销过程：

```cpp
1. 加载 vptr：     p → vptr                       (1 次内存访问，可能 cache miss)
2. vtable 查找：   vptr[foo_index] → 函数指针     (再 1 次访问)
3. 间接调用：      call rax                       (破坏了 CPU 的分支预测)
```

### 3.4 跨编译单元 / 动态链接的函数

```cpp
// libfoo.so 里的函数
extern int foo(int);

// 运行时
foo(42);
```

额外开销：

- **动态符号解析**：第一次调用要查 GOT/PLT（lazy binding）
- **完全失去内联机会**：编译器看不到函数体
- **可能引发 cache miss**：跨 `.so` 边界，指令地址空间不连续

## 4. 硬件层面的隐性开销

除了上面那些"指令级"成本，还有几个 CPU 流水线层面的隐性开销，**单次不可见，热点路径上会累积成巨大差距**。

### 4.1 间接跳转破坏分支预测

```cpp
p->foo();        // 虚函数：目标地址是运行时才知道的
int (*fp)(int);  // 函数指针
fp(42);
```

CPU 的 **BTB（Branch Target Buffer）** 能记住"上次这条跳转去了哪里"，但如果**目标地址每次都不同**（多态虚函数、运行时函数指针），预测命中率暴跌 → **流水线冲刷**。

多态虚函数的实际代价：可能 **10~30 cycle** 的预测失败开销。

### 4.2 i-cache 污染

大函数被调用后，**i-cache（指令缓存）** 会被刷掉一部分，下次再调别的函数时又 miss。

L1 i-cache 典型 32 KB：一个 50 KB 的函数不可能完整装下，每次调用都要从 L2/L3 拉。

### 4.3 栈帧过大破坏 d-cache

栈上的局部变量如果太大，会挤掉其他热点数据的 cache 位置。

### 4.4 返回地址预测失败

CPU 有 **RAS（Return Address Stack）** 专门预测 RET 指令。深度调用 + 异常路径会让 RAS 容量溢出（典型 16~32 项），预测失败 → 又一次流水线冲刷。

## 5. 各种调用方式的开销对比

|调用方式|典型 cycle 开销|备注|
|---|---|---|
|内联（`inline`）|0|编译器做|
|普通静态函数|5~15|—|
|大函数（栈帧大）|20~50|栈分配 + cache 效应|
|虚函数（单态）|5~15|间接调用但可预测|
|虚函数（多态）|15~40|预测失败、cache miss|
|函数指针（稳定）|5~15|—|
|函数指针（多变）|15~40|—|
|跨 `.so`（首次）|50~200|PLT/GOT 解析|
|跨 `.so`（稳态）|10~30|仍无内联机会|
|跨进程 (RPC / 系统调用)|1000~100000|上下文切换 + 内核态|

## 6. 为什么有时候"开销大但还是要用"？

```text
                    函数调用开销
                          │
                          ▼
                ┌───────────────────┐
                │ 能否被编译器消除？ │
                └─────────┬─────────┘
                          │
         ┌────────────────┼────────────────┐
         ▼                ▼                ▼
    静态可见          动态多态         跨边界
         │                │                │
     自动 inline       必须 vtable       必须 call
         │                │                │
   开销 ≈ 0         开销 5~40       开销 10~1000s
```

必要场景：

- **必须用虚函数**：多态场景（运行时才知道类型）
- **必须用动态库**：模块解耦、动态加载
- **必须用 RPC**：跨机器、跨服务

这些场景里，调用开销是**必要的代价**。优化方向不是消灭它，而是减少它：

- **缓存预热**：把热函数指针稳定下来
- **devirtualization**：编译器基于类型推导把虚调用转成直接调用
- **PGO（Profile-Guided Optimization）**：运行时收集 profile，让编译器优化热点路径
- **`final` 关键字**：告诉编译器没子类，可去虚拟化
